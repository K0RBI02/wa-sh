# wa:sh – Development

Everything about building, testing and releasing. What the app does is in the [README](../README.md).

## Build

Requirements: [Flutter SDK](https://docs.flutter.dev/get-started/install) (stable), plus Xcode for iOS.

```bash
git clone git@github.com:K0RBI02/wa-sh.git && cd wa-sh
python3 tool/setup.py   # creates the plugin, android/ and ios/, adds permissions, builds the icon
flutter run
```

`android/`, `ios/` and `packages/wash_live/` are intentionally not in the repo: they
are generated by `tool/setup.py` from the sources under `tool/`. After changing
anything there, just run the script again.

`tool/setup.py` does everything that can be automated:

- creates the plugin `packages/wash_live` and copies in the native sources from
  `tool/wash_live/` (Android: Java service, manifest, status bar icon; iOS: Swift)
- runs `flutter create` for the app, then patches **Android:** permissions,
  `flutter_local_notifications` receivers, core library desugaring, app name, release
  signing, backup rules, predictive back; **iOS:** app name, `NSSupportsLiveActivities`,
  URL scheme `wash://`, local network access
- places the widget extension files in `ios/WashLiveWidget/`
- generates the app icon (`flutter_launcher_icons`)

### Android note

If `JAVA_TOOL_OPTIONS` is set (e.g. for UI scaling), Gradle's JDK detection trips
over it. Workaround: `env -u JAVA_TOOL_OPTIONS flutter run`, or an alias.

### iOS: set up the Live Activity (once, on a Mac)

A widget extension can only be created as its own target in Xcode:

1. `open ios/Runner.xcworkspace`
2. *File → New → Target… → Widget Extension*, name **WashLiveWidget**,
   untick *Include Live Activity* (we bring our own files), confirm *Activate*.
3. Delete the Swift files Xcode generated in the *WashLiveWidget* folder and add
   `ios/WashLiveWidget/WashLiveWidget.swift` and
   `ios/WashLiveWidget/WashLiveAttributes.swift` to the **WashLiveWidget** target instead.
4. Set the deployment target of *WashLiveWidget* to **iOS 16.2**.
5. Build. On the first timer iOS asks whether Live Activities are allowed.

Without the extension the app still runs on iOS – just without a Live Activity.

So that “done” breaks through a Focus: add **Time Sensitive Notifications** to the
*Runner* target under *Signing & Capabilities*.

If notifications don't appear while the app is open on iOS, add this at launch in
`ios/Runner/AppDelegate.swift`:

```swift
UNUserNotificationCenter.current().delegate = self as? UNUserNotificationCenterDelegate
```

Newer Flutter templates use a `SceneDelegate`. If the Live Activity buttons
(“Already done”, “Overview”) don't reach the app, the scene delegate has to
forward the `wash://` links – tapping the Live Activity itself always opens the app.

## Links and NFC

`wash://start?machine=wash&program=1` (`program` 1 or 2) or
`wash://start?machine=dry&minutes=90&name=Quick%2030°` starts a timer right away;
if the machine is already running the app just opens it. Android handles the link
from browsers, other apps and NFC tags (NDEF URI record); iOS via the URL scheme,
e.g. from a Shortcuts automation. Encode spaces as `%20`, not `+`.

The website in `docs/index.html` (GitHub Pages, *Settings → Pages → main /docs*)
writes such links to NFC stickers via Web NFC (Chrome on Android).

## Notifications

Android groups notifications by machine; every category can be switched off or
adjusted on its own (sound, vibration, Do Not Disturb):

| Washer / Dryer | When | Default |
|---|---|---|
| Running | persistent, with time left and progress | silent |
| Almost done | 10 minutes before the end | normal |
| Done | at the end | high |
| Nudges | “remind me again”, “not collected yet?” | normal |

Channel IDs: `<machine>_running`, `<machine>_soon`, `<machine>_done`, `<machine>_nudge`
with `<machine>` = `wash` | `dry`, in the channel groups `wash` and `dry`.
On iOS notifications are threaded per machine.

## Tests

```bash
flutter analyze
flutter test        # core logic: durations, parallel machines, persistence, HA pairing

pip install pytest-homeassistant-custom-component
python -m pytest    # Home Assistant integration against a real Home Assistant
```

Two GitHub Actions workflows:

- **CI** (app): setup, analyze, tests, release APK as an artifact under *Actions → Artifacts*.
  Skipped when only the integration or Markdown files change.
- **Home Assistant**: pytest, `hassfest`, HACS validation.

## Release

**Signing (once):**

```bash
keytool -genkey -v -keystore ~/wa-sh-upload.jks -keyalg RSA -keysize 2048 -validity 10000 -alias wash
```

Locally, create `android/key.properties` (not committed):

```properties
storePassword=…
keyPassword=…
keyAlias=wash
storeFile=/home/<you>/wa-sh-upload.jks
```

then `flutter build apk --release`.

For CI, add under *Settings → Secrets and variables → Actions*:
`KEYSTORE_BASE64` (`base64 -w0 ~/wa-sh-upload.jks`), `KEYSTORE_PASSWORD`, `KEY_ALIAS`,
`KEY_PASSWORD`. Without secrets CI signs with the debug key.

**Publish a version:** bump `version:` in `pubspec.yaml` (and `version` in
`custom_components/wash/manifest.json`), update `CHANGELOG.md`, then

```bash
git tag v0.4.0 && git push --tags
```

CI builds the APK and attaches it to a GitHub release; HACS shows the tag as the version.

### F-Droid

F-Droid builds the app from source and signs it itself. The recipe is in
[`docs/fdroid/de.k0rbi02.wash.yml`](fdroid/de.k0rbi02.wash.yml); store texts, icon and
feature graphic come from `fastlane/metadata/android/` automatically.

1. Tag a release (`v0.5.0`) – the recipe builds from tags.
2. Fork [fdroiddata](https://gitlab.com/fdroid/fdroiddata) on GitLab, copy the recipe to
   `metadata/de.k0rbi02.wash.yml`, check the Flutter version in `srclibs`.
3. Test locally if you like: `fdroid readmeta && fdroid build -v -l de.k0rbi02.wash`.
4. Open a merge request (“New app: wa:sh”). The F-Droid team reviews it; once merged,
   new tags are picked up automatically (`UpdateCheckMode: Tags`).

Store listings for F-Droid / Play live in `fastlane/metadata/android/` (`en-US`, `de-DE`),
privacy notes in [`PRIVACY.md`](../PRIVACY.md), all changes in [`CHANGELOG.md`](../CHANGELOG.md).

The README images are generated from the app's doodles: `python3 tool/doodles_to_svg.py`.

## Languages

All texts live in `lib/l10n.dart` (German and English, no code generator – texts are
also needed outside widgets, e.g. for notifications and quick actions). The app follows
the system language and switches live; Android 13+ and iOS also offer a per-app
language setting. The native “running” display (Java/Swift) picks the language itself.

## Accessibility

With the system setting “reduce motion” all animations stand still. Text size
follows the system setting up to 130 %; all controls have screen reader labels
and are at least 44 px.
